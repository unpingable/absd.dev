ABSD — An experimental operating system.

ABSD is a small operating system written in Rust. It boots under QEMU, runs isolated processes, keeps files across reboots, and is administered over stock OpenSSH. Its userspace includes a shell, commands, manual pages, and some unmodified Rust programs.

Try ABSD

Binary developer preview absd-preview-rc1 (state published): what works, what does not, and how to try it on a Linux x86-64 host with QEMU, with no build tools. To build from source instead, follow the source release's README; status says what each does and does not show.

ABSD is experimental, single-operator software, not ready for production. SSH sessions share the operator's files; they are not separate user accounts. No physical hardware is supported. How sessions are isolated.

There is no fork, no user IDs, and existing Unix or Linux software needs porting. The published RC1 preview has no staged upgrade or rollback; a newer preview requires a new machine. Read the selected release's instructions and limits before running it.

One developer directs the work. AI coding agents wrote most of the code, tests, documentation and reviews; no independent human audit has been done. How ABSD is developed.

What distinguishes it

Isolation
Every program is a separate process in its own address space, started by spawn; there is no fork. A process can act only on itself and its own children; a few whole-system counts are readable by any process. Design: spawn, not fork.
Explicit authority
A process can touch only what it was handed: handles to kernel objects, each carrying rights that can be dropped and never added. There are no user IDs and no ambient privilege. This is the capability model of earlier systems, not a new invention. Design: handles and rights.
Bounded scheduling and recovery
Bounds are fixed limits, not timing guarantees: 16 processes in the whole system and four SSH connections by default. Processes are preempted by a timer; the experimental periodic scheduling class has no real-time guarantee. Failure handling and its evidence depend on the revision. Design: replacement is not recovery.
Evidence-oriented engineering
Claims on the status, design, hardware, and evidence pages carry a label saying how strongly each is supported, in which environment, and where the claim stops. Failed runs stay on record. How statements are labelled.
