About

ABSD is an experimental operating system by James Beck. The kernel and userspace are written in Rust. Its source is public at github.com/unpingable/absd under the Apache License 2.0, as source releases assembled from the repositories where development happens. It can be built and booted under QEMU by following that repository's README; no images or packages are offered here.

Why it exists

Most systems grant a program broad authority by default and report success loosely: a program can usually do whatever its user can, and "written" may mean "in a cache". The rules that matter (who may do what, what happens when something fails, what survives a crash) are then enforced defensively on top. ABSD began as a way to test whether those rules could instead be native, and still survive contact with real operating-system workloads. It now runs enough software (an SSH server, a file server, a shell, commands, and real programs from another project) to be its own testbed.

The ideas are not new. Capability systems such as KeyKOS, EROS, seL4, and Zircon made authority explicit long before ABSD, and crash-consistency research made storage guarantees testable. ABSD's interest is in putting them together in one small system and recording honestly where that holds and where it does not. The research program page says more.

What it is for

  • Studying how a small system behaves when authority, failure, and durability are stated explicitly and checked.
  • Running as a single-operator specialist VM under QEMU, administered over SSH.
  • A testbed for real programs whose storage and failure behaviour can be compared with their Linux builds.

What it is not for

  • Running on physical hardware: physical hardware qualification is not yet established.
  • Production use, multi-user systems, or anything that must stay up.
  • Running existing Unix or Linux software without porting; see compatibility.
  • Replacing a BSD or Linux system.

How it is developed

One developer, James Beck, directs the work: deciding what is built, setting the acceptance rules, and accepting or rejecting results. AI coding agents wrote most of the code, tests, and documentation, including most of the text of this site.

Review is also done by AI: releases and merges are accepted after a review by AI model sessions separate from the ones that did the work. That catches some errors and is not independent human review. No outside person has audited ABSD's design, code, or tests, and no human security review has been done. Read "qualified", "validated", and "accepted" on this site as "the recorded checks passed and were re-examined by a separate AI session", and nothing stronger.

This is why the site leans on what can be checked without trusting the author: named environments, recorded runs, counts taken from the check scripts' own output, checks that are shown able to fail, and failures kept on record. The method is described under bounded acceptance.

Publishing the source is what makes independent checking possible; it has not happened yet. Two limits remain even with the source in hand. The review records and the receipts of earlier runs are not in the public tree. And the checks that run programs from the author's other projects on ABSD (the extended integration profile) cannot be re-run from a public clone, because those projects' sources are not in it; what a public clone can re-run is the kernel's suite and the platform gate's core profile. See status.

Relation to BSD

The operating system's commands, manual, and conventions follow BSD practice where the semantics match. ABSD is not derived from BSD source and is not a BSD distribution.

Licence

ABSD's own source (the kernel, the platform, the tools and the tests written for it) is licensed under the Apache License, Version 2.0. Three distinctions go with that:

  • Third-party material in the tree keeps its own licences, as do libraries downloaded at build time. The repository lists them in THIRD-PARTY.md, and LICENSING.md says what applies to what.
  • A boot image built from the source additionally contains GRUB (GPL-3.0-or-later) and a font from the build host's GRUB package. The source tree does not carry them; a built image does, and redistributing an image carries GRUB's obligations.
  • Files written for ABSD carry no licence header and no copyright line yet. ABSD was written largely by AI coding agents directed by one developer; what copyright subsists in such code is an open legal question, and the licence grant does not settle it.

The licence covers the operating system's repository. It is not a licence for this site's text.

Following and contributing

The source is at github.com/unpingable/absd. That repository is a source release, not where development happens: it is assembled from the development repositories at exact revisions, and it changes only when a release is made. That shapes what happens to a contribution (the repository's CONTRIBUTING.md and RELEASING.md are the authoritative texts):

  • Issues are read and answered on the public repository. A report that names the release, the host, the command and its output is the most useful kind.
  • Pull requests are read there as proposals. They are never merged there directly, because the next release would overwrite them.
  • An accepted change is applied in the development repository of the component it touches, with its author recorded, and goes through the same checks as any other change. It appears in the public repository in a later source release. Acceptance is the change arriving in a release, not the state of the pull request.
  • Small fixes with a test, reproducible failures, and corrections to documents that claim more than their evidence are the easy cases. Larger changes are unlikely to be accepted as pull requests; open an issue first.
  • Contributions to ABSD's own source are accepted under the Apache License 2.0. Say where code came from, and say so if an AI system wrote or helped write it.

To follow the project:

  • Progress is recorded on this site when a milestone or release is accepted: evidence lists the records newest first, and status lists what has been accepted since the last milestone.
  • This site's own source is public at github.com/unpingable/absd.dev. It contains the pages and the milestone's manual sources, not the operating system. Every change to a claim on this site is a commit there, so watching that repository is the way to be told when something changes.
  • Corrections to this site: issues on the site's repository. A claim on this site that its record does not support is a bug. Problems with the system itself belong on the source repository.
  • Related public work by the same author is listed on the research page.
